## Aspect ratio correction for webcam landmarks (2026-11-02)

The browser now rescales landmark y to a 16:9 reference before sending or recording (`toFrame(r, aspect)` in `frontend/src/lib/landmarks.ts`: factor (16/9) divided by the video aspect, so 4/3 for a 640x480 webcam; x and z unchanged, backend unchanged). Reason: MediaPipe y is a fraction of the image height, the model was trained on 16:9 INCLUDE videos, and the fake camera test gave wrong or missing signs on 4:3 input. The Landmark check file records `reference_aspect` and `video_aspect`, and `training.compare_landmarks` applies the same rescaling to the Python landmarks for files that carry the field (older files are compared as before). Tests: `landmarks.test.ts`, `landmarkCheck.test.ts`, `test_compare_landmarks.py`.

One fake camera re-run (the same INCLUDE test videos as a 640x480 letterboxed camera, headless Chrome with a low extraction rate, one run each): Hat is still correct (HAT 99.6 percent isolated, HAT in continuous mode). Doctor changed from a skirt sign to DOCTOR (95 percent) in continuous mode, but the isolated button still said unrecognized (best guess Brown 23 percent) and continuous mode also produced two SLOW detections. Yesterday changed from a wrong sign (THEY) to unrecognized (best guess Cell phone 56 percent, below the 0.7 threshold). So the change removed the confident wrong answers in this test but did not make recognition reliable. This is three videos on one fake camera setup, not a measurement; real webcam takes from real signers (the guided recordings) are the test that counts. It is a reasoned change of the live input, not a retrained model, and no number in `docs/evaluation` is affected. Recordings made before this change carry uncorrected y and should be re-recorded or scaled before they are mixed with new ones.

## Landmark check: browser versus Python MediaPipe (2026-10-31 11:00)

Why: the model was trained on landmarks that Python MediaPipe extracted from INCLUDE videos (about 1080p, recorded by the authors), while the live app uses the WebAssembly build with CPU inference on a 640x480 webcam image. The recorder stores landmarks only, so the same take could not be run through Python MediaPipe. New tab "Landmark check": a 3-2-1 countdown, then a 4 second MediaRecorder video of the camera and, at the same time, the landmarks the browser extracts, each with its time in the video. Both are offered as downloads (video and `.landmarks.json`); nothing is uploaded and no server call is made. `python -m training.compare_landmarks --video <file> --landmarks <file>` (from `backend/`) then runs Python MediaPipe Holistic on the video with the training options, pairs frames by time, normalizes both sets with the same `normalize_frame`, and reports: distance between the two landmark sets in shoulder widths (33 pose points, arms from shoulder to wrist, each hand: median, mean, p95), how often each side detected the pose and each hand (both, browser only, Python only, neither), the browser extraction rate, and the model's top 3 predictions from each landmark set. It also prints a scale: a hand is about 0.4 to 0.5 shoulder widths across, so 0.05 or less is small and above 0.15 large (rule of thumb of mine, not a validated threshold).

Checked without a camera: 6 unit tests for pairing, distance (a known shift gives exactly the expected value), detection counting and file errors; 4 frontend tests for the file builder; and an end to end run on a real INCLUDE video (Colours/Pink, 70 frames): the Python side extracted it, I built a stand-in "browser" file from the same landmarks with added noise (0.003 image units), and the tool paired 47 frames, reported arm distance 0.051 and hand distances 0.046 to 0.082 shoulder widths, full detection agreement, and the model predicted Pink (0.897) from the stand-in set. This shows the tool works; it says nothing yet about the real browser, because the browser pane blocks the camera and no real webcam take exists. The extracted trial video was deleted.

How to use it: open Landmark check, start the camera, sign one sign you know, Record, download both files, run the printed command, and send me the report. Decide about the model only after that: if the arms and hands differ by more than about 0.15 shoulder widths, or the browser misses hands Python finds, the fix is probably in extraction (resolution, smoothing, camera framing), not in the classifier.
